# Адаптация BrandRadar: последовательность и границы

Исходный commit: `4254f75ee158098b61b7a5ea061254246c7be84e`. Владелец подтвердил допустимость заготовки. Перенос кода не означает готовность банковской аналитики. Исходники baseline не переписываем в том же коммите, что импорт: происхождение и новая работа различимы.

## Решение по стеку

Сохраняем Go/Gin + PostgreSQL, React/TypeScript и Python/FastAPI. Go — публичный API, доступ, состояние analysis run, исполнитель плана и инструменты, жизненный цикл/лимиты задания. Python — индексирование/поиск, извлечение, структурированный план/анализ/проверка через разрешённую LLM и учёт вызовов провайдера. Не создавать вторую независимую машину состояний в Python. Redis оставить для текущих нужд до замеров; MinIO нужен старым моделям, для нового API-пути его обязательность проверить. Файлы пока не удалены.

## Этап 0: база и работоспособность

- Сверить 379 SHA с import-manifest, сохранить notices.
- Зафиксировать единственный пакетный менеджер frontend: сейчас Docker использует Bun, присутствует и npm lock. Разобрать peer-конфликты; не обходить их `--force` как финальное решение.
- Реализовать отключаемые старые ML-зависимости, безопасный mock и health без скачивания неразрешённых весов. Разделить сбор/сохранение источников и анализ: сейчас сбой ML останавливает весь tick.
- Уточнить, какие старые тесты требуют внешних моделей/сервисов; вести команды и результаты в отчёте, не заявлять весь стенд проверенным.

## Этап 1: согласованный вертикальный сценарий

Роман Аксенов даёт синтетический CompanyContext и 3 профиля. Павел — документ новости и банка с locator. Роман Шваров — analysis-run API и состояния. Денис — типизированный mock, затем адаптер разрешённой модели. Вера — выдача одного insight с явным mock и ссылками. Общие fixtures проходят через UI/API/Python без отдельной ручной подмены полей.

Готовность: из чистого запуска можно выбрать клиента и получить карточку; каждый текстовый вывод имеет основания. Mock не считается готовым AI.

## Этап 2: ядро кейса

Профили реальных обезличенных данных (без публикации) → персональный поиск/ранг → релевантная аналитика банка → многошаговый анализ → VERIFY → уточнённый поиск максимум один раз → DONE/PARTIAL. Обязательны новая новость, разные компании/роли, неполные поля и противоречащие источники.

## Этап 3: качество и сдача

Holdout, сравнение baseline, фактические cost/latency, бюджет 500 ₽ на всю команду, защита доступа, внешняя среда после согласования аренды, lockfiles, notices, README и релизный tag. Детали в evaluation/deployment.

## Что не делать первым

Массово переименовывать Go module или каждый BrandRadar-компонент, переписывать Go на Python, переносить метрики тональности как метрики качества инсайтов, обучать старые модели заново, добавлять автономную агентную платформу. Переименования и удаление legacy — отдельные ограниченные задачи после рабочего сценария.

## Передача агенту

Каждый участник выбирает одну задачу A1–A3 своего role-файла, фиксирует ветку, входы и reviewer в implementation note. Агент изучает существующие компоненты, выполняет ограниченный цикл из AGENTS.md, проверяет наблюдаемое поведение, обновляет note и открывает PR. Не отдавать двум агентам общий checkout или одну миграцию. Агентов разработки не включать в runtime продукта.
