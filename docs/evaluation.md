# Оценка и критерии приёмки

Числа ниже — предлагаемые цели MVP, не результаты измерений. R2 согласует с командой и публикует фактический отчёт, включая неудачи.

Подготовить минимум 30 оценённых пар компания–событие, минимум 3 профиля; разметка релевантности 0/1/2 и доказательств двумя участниками, разногласия разобрать. Разделить по событиям и времени: дубли одного события не должны попасть и в настройку, и в holdout. Добавить новую новость, противоречащие документы, пропуски, prompt injection и устаревшую аналитику.

- Персонализация: Precision@5 и nDCG@5 против общей ленты по свежести и отраслевого baseline. Цель P@5 ≥ 0.8 на размеченном holdout; размер выборки и неопределённость указать.
- Доказательства: 100% отображаемых ссылок разрешаются; доля поддержанных источниками утверждений оценивается вручную. Неподдержанные числовые эффекты/выдуманная позиция банка — блокирующий дефект.
- Польза: экспертная оценка конкретности влияния и действий 1–5, время выбора трёх значимых событий, обратная связь UI.
- Агентная логика: трасса показывает план, инструменты, общий контекст и VERIFY; на кейсе нехватки — повтор поиска и честный partial при исчерпании лимита.
- Устойчивость: новый материал проходит без правки кода; отсутствующий кредитный признак не означает отсутствие кредита; временные конфликты объясняются.
- Эксплуатация: p50/p95 отдельно по режимам, стоимость/insight, cache hit, ошибки JSON, таймауты; бюджет ≤ 500 ₽/день на всю команду при подтверждённых тарифах. Числовую цель latency определить после первого замера.
- Безопасность: нет утечки между компаниями; инструкции из источника не вызывают инструменты; журналы без ключей и сырых чувствительных данных.

Обязательные интеграционные проверки: CSV→профиль; материал→источник→карточка; same news/different company; API timeout; бюджет при конкурентных вызовах; запрет чужого company/run/source. Тестировать поведение и границы, не только соответствие собственной реализации.
